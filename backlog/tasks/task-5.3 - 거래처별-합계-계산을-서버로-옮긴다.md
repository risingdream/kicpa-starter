## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
1일차 4강. 5.2에서는 화면이 증빙 목록을 받아 거래처별 합계를 직접 더했다. 이 계산을 서버가 맡게 옮긴다. 금액 규칙은 서버 한곳에서 지켜야 화면이 여럿이 되어도 숫자가 같다.

- API: GET /api/receipts/by-vendor. 응답은 {"items": [{"vendor", "count", "supply", "vat"}, …], "total": {"count", "supply", "vat"}}. 증빙이 없으면 items는 빈 목록, total은 모두 0이고 상태 코드는 200이다.
- 화면: 거래처별 합계 표와 전체 합계 행은 이 주소가 준 값을 그대로 보인다. items가 비면 표 대신 '표시할 거래가 없습니다'를 보인다.
- 업무 규칙 테스트: 집계 계산을 DB 없이 도는 함수로 두고, 입력을 직접 넣어 확인한다(가상 증빙 3건, 공급가액 1,005원 증빙 2건, 음수 반품).

계획 검토 때 사람이 정할 것: 화면이 지금 거래처의 부가세 합계를 어느 기준으로 더하는지 보고, 서버로 옮길 때 어느 기준으로 할지 정한다(공급가액 합계의 10%인가, 건별 부가세의 합인가). 장부 목록의 부가세 칸은 증빙 한 건마다 원 미만을 버린 값이다. 공급가액 1,005원 증빙 2건이면 건별 합은 100+100=200원, 합계의 10%는 2,010×10%=201원이다. 강의용 비교이며 세법상 처리 기준을 정하는 것은 아니다.

강의 시간 안에 끝나지 않으면 완성본 브랜치 v2/d1-done으로 바꾼다(docs/checkpoints.md).

하지 말 것: DB 표 구조(stack/db/init.sql) 수정, 기존 GET /api/receipts 응답 변경, 5.2에서 만든 표 모양 바꾸기, 거래처 편집·삭제 기능
